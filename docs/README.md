# Документация

Документация pysatl-mpest: Sphinx-проект в `source/`, сборка в `build/html`. При пуше в `main` workflow `.github/workflows/docs.yml` собирает её и публикует на GitHub Pages.

```bash
poetry run make -C docs html                      # сборка, как в CI
poetry run python docs/tools/export_diagrams.py   # PNG из всех листов .drawio
```

Вне Sphinx лежат исходные материалы: `review/` — обзор литературы, `requirements_dashboard.html` и `usecases_dashboard.html` — дашборды требований и сценариев.

## Диаграммы

- Источник — `.drawio`, внутри листы; PNG каждого листа лежит рядом: `<файл>.<id листа>.png`. PNG не правится руками, только экспортом (`tools/export_diagrams.py`; нужен draw.io CLI 27.0.2+). Правка диаграммы и обновление PNG — один коммит.
- Диаграммы лежат в `diagrams/` рядом с документом, который их объясняет. Верхний уровень — `source/design/diagrams/`, модуль — `source/design/modules/<модуль>/diagrams/<модуль>.drawio`.
- Id листа — kebab-case, имя листа — по-английски. Листы модуля идут в порядке: `overview`, страницы подмодулей, затем `seq-*` (sequence). `overview` — диаграмма классов модуля в UML: классы с публичными свойствами и методами (аргументы и тип результата), приватный модуль-утилита — блок `«module»` со списком функций; соседние пакеты — рамки (`umlFrame`) только с классами, связанными с модулем; связи — наследование, агрегация с кратностью, зависимость. Верхнеуровневые: `full-architecture` (`system-context`), `module-architecture` (`overview`, `detailed`), `usecases`, `sequences` (`seq-*`), `activity`, `algorithms-tree`.
- **Диаграмма должна помещаться в страницу документации:** ширина листа не больше ~900 px, высота не больше ~650 px (в границах всех блоков, включая заголовок и легенду), шрифт на блоках не мельче 11 pt. Ширина — жёсткий предел. Высоту можно немного превысить, если лист читается целиком. Если диаграмма заметно не влезает, она делится на несколько листов, а не уменьшается. Размер проверяется по PNG.
- Без пояснительного текста на диаграммах: только заголовок, имена элементов (как в коде) и подписи связей там, где без них не понять; пояснения идут в md. Статус элемента (planned, external) передаётся стилем и легендой, а не словом в блоке.
- Легенда — панель `Legend` (draw.io `swimlane`, тонкая рамка, заголовок 10 pt жирный) в нижнем углу листа. Внутри маленькие образцы стиля 24×14 той же формы, что элементы листа (прямоугольник, овал, скруглённый блок), подпись 10 pt справа от образца. Подпись в самом образце не пишется, чтобы легенду нельзя было принять за блоки схемы.
- Подписи на диаграммах английские. Имена классов и модулей пишутся как в коде.
- Диаграмма показывает код как он есть. Модули, которых ещё нет в коде, рисуются стилем *planned*: пунктирная рамка `dashed=1`, серые обводка и текст `#666666`, белая заливка.
- Стиль: чёрно-белый, `Helvetica`; обычный блок — белая заливка и чёрная обводка 1.5; внешняя зависимость (`pysatl-core`, `numpy`, `scipy`) — заливка `#F2F2F2`. Зависимость `A → B` («A использует B») — пунктирная стрелка, наследование — сплошная с полым треугольником. Заголовок листа — текстовая ячейка слева сверху, 18 pt, жирный.
- В исходнике страницы диаграмму задаёт отдельный абзац со ссылкой на `.drawio` и названиями листов в title, например `[Исходник схемы](diagrams/core.drawio "Overview")`. Расширение `source/_ext/drawio_viewer.py` показывает перечисленные листы над ссылкой и центрирует ссылку под ними. PNG-экспорт нужен для ревью и просмотра вне сайта. В тёмной теме `source/_static/drawio-viewer.css` инвертирует цвета, поэтому диаграммы строго чёрно-белые, без цветных заливок.
- Просмотр изменений: `DRAWIO_DIFF_NO_OPEN=1 git drawiodiff [<коммит>] -- <файл>.drawio`.

## Текст

- Страница: `# Заголовок`, затем строка `**Назначение:** …`; один H1, заголовки без скачков; абзац — одна строка; ссылки — относительные.
- Текст русский; имена классов, модулей и параметров — как в коде, в обратных кавычках.
- Страница модуля (`source/design/modules/<модуль>/<модуль>.md`) отвечает на вопрос «как устроено, почему так и на что наткнёшься при изменении»; «как вызвать» — в `source/api/`. Разделы по порядку:
  1. Заголовок и `**Назначение:**`.
  2. «Состав модуля» — файлы, что публично и что приватно, по строке на файл.
  3. «Диаграмма классов» — viewer листа `Overview` и пункты о том, чего не видно из рисунка: кто и зачем использует модуль, что сознательно не нарисовано.
  4. Устройство — подраздел на каждый неочевидный механизм (инвариант, проектное решение и его причина), а не на каждый метод. Дополнительный лист (`seq-*`) вставляется в подраздел, который он объясняет.
  5. «Как расширить» — только если у модуля есть точка расширения.
  6. «Ограничения» — известные ограничения и недоработки, в том числе те, что решено пока не чинить.
- На странице реализованного модуля не пишутся: сигнатуры, параметры и исключения методов (их генерирует `source/api/`, на него ставится ссылка), математика (раздел «Материалы»), сквозной сценарий через несколько модулей (`architecture.md`, `behavior.md`).
- Описывается то, что есть в коде; планируемое помечается «Запланировано». Страница запланированного модуля содержит назначение, а пока модуль готовится к реализации — и его дизайн с сигнатурами, как у `initializers`: справочника API для ненаписанного кода ещё нет. После реализации сигнатуры уходят в справочник, а страница приводится к правилам реализованного модуля.
