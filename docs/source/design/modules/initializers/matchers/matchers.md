# Сопоставление кластеров и семейств
**Назначение:** описать роль `Matcher` модуля [`initializers`](../initializers.md) и её реализации: какой кластер достаётся какому семейству (Запланировано).

Сопоставление — действие 4 в {ref}`ходе initialize <init-walk>`. Сопоставитель видит только протокол {ref}`ComponentTable <init-component-table>`: $\ell_{jc}$, причины невозможных пар, средние кластеров и группы {ref}`одинаковых семейств <init-identical-families>`.

## Контракт

`Matcher.match(table: ComponentTable) -> UnivariateIntArray` возвращает перестановку `assignment`: `families[j]` получает кластер `assignment[j]`. `match` — шаблонный метод:

```python
class Matcher(ABC):
    @final
    def match(self, table: ComponentTable) -> UnivariateIntArray:
        return self._order(self._match(table), table)

    @abstractmethod
    def _match(self, table: ComponentTable) -> UnivariateIntArray: ...

    def _order(self, assignment: UnivariateIntArray, table: ComponentTable) -> UnivariateIntArray:
        return order_identical(assignment, table.groups(), table.cluster_means())
```

- **Результат — перестановка `0…k−1`,** иначе `ClusterInitializer` бросит `ValueError`.
- **`_match` решает, какие кластеры каким семействам;** внутри группы одинаковых семейств распределение наводит `_order`, и свой сопоставитель его нарушить не может. Хук переопределяют, только если порядок задаёт кто-то другой — из встроенных так делает `IdentityMatcher`.
- **Только через протокол:** $\ell_{jc}$ и причины — из таблицы, без повторной оценки; к `X`, `H` и оценщику сопоставитель не обращается, компоненты и смеси не собирает.

| Сопоставитель | Как раздаёт | Статус |
| --- | --- | --- |
| `HungarianMatcher` | Максимум суммы $\ell_{jc}$ по парам, венгерский алгоритм | Первая версия, по умолчанию |
| `IdentityMatcher` | Кластер `j` — семейству `j`, как отдал способ разбиения | Первая версия |
| `ExhaustiveMatcher` | Максимум правдоподобия всей смеси, перебор раздач | Позже, см. {ref}`«Первая версия» <init-first-version>` |

## Зачем сопоставлять

Кластеры не упорядочены. Если все семейства одинаковые, раздача не важна: смесь та же с точностью до порядка, а `MixtureModel.__eq__` от порядка не зависит. В гетерогенной смеси раздача решает: `Exponential` на кластере с отрицательными точками даёт нулевое правдоподобие на них.

Обозначения: $\sigma(j)$ — столбец семейства $j$, $\gamma_{ic}$ — элементы `H`, $\hat\theta_{jc}$ — параметры компоненты из таблицы.

(init-order-identical)=
## Порядок одинаковых семейств

Номера кластеров произвольны (метки `KMeans` от запуска к запуску разные), а внутри группы одинаковых семейств `linear_sum_assignment` тоже раздаёт произвольно: строки группы совпадают. Без нормализации у `[normal, normal]` компонента 0 была бы то левой, то правой модой, и настройки `ECM` по номеру применялись бы к разным модам.

Поэтому `_order` по умолчанию вызывает чистую `_matching.order_identical(assignment, groups, means)`: в каждой группе кластеры группы переставляются по возрастанию среднего, при равных средних раньше идёт меньший номер столбца.

- Пример: группе `[0, 2]` из `[normal, expon, normal]` достались кластеры со средними 7 и 1 — после `_order` `families[0]` получает среднее 1, `families[2]` — 7.
- Смесь не меняется: одинаковые семейства взаимозаменяемы, сумма $\ell_{jc}$ та же.
- Тесты: литералы и свойство — результат перестановка, множество кластеров группы не изменилось, средние внутри группы не убывают.

(init-hungarian)=
## Критерий по парам: `HungarianMatcher`

Пара оценивается логарифмом правдоподобия точек кластера при оценённой компоненте, раздача — суммой по выбранным парам:

$$
\ell_{jc} = \sum_{i \in C_c} \log f_j\bigl(x_i \mid \hat\theta_{jc}\bigr), \qquad C_c = \{\, i : \gamma_{ic} = 1 \,\},
$$

$$
\sigma^{*} = \arg\max_{\sigma \in S_k} \sum_{j=1}^{k} \ell_{j\sigma(j)}.
$$

- Сумма только по точкам кластера: в сумме по всей выборке с весами у точки вне кластера и вне носителя $0 \cdot (-\infty)$ даёт `NaN` и портит всю матрицу.
- Это классификационное правдоподобие при фиксированных кластерах. Сумма, а не среднее: каждый кластер входит в раздачу ровно раз, и сумма — правдоподобие всей выборки. Веса и штраф за число параметров от раздачи не зависят.
- Критерий аддитивен, поэтому это линейная задача о назначениях: `scipy.optimize.linear_sum_assignment` решает её точно за $O(k^3)$.

[Исходник схемы сопоставления](../diagrams/initializers.drawio "Sequence: matching")

`HungarianMatcher._match(table)`:

1. Если группа одинаковых семейств одна (`table.groups()`), возвращает тождественную перестановку и ничего не оценивает.
2. Строит `cost` размера `k × k`, `cost[j, c]` $= -\ell_{jc}$ из `table.loglikelihood(j, c)`; строки одинаковых семейств берутся из общих записей таблицы.
3. Вызывает `_matching.solve_assignment(cost)` и получает перестановку или `None`.
4. При `None` бросает `InitializationError` «нет раздачи, где каждое семейство получает подходящий кластер» со всеми парами $\ell_{jc} = -\infty$ и причинами из `table.failure(j, c)`, например «семейство 0 (`Exponential`), кластер 1: 3 точки кластера вне носителя, например −1.0».

[Исходник схемы solve_assignment](../diagrams/initializers.drawio "Sequence: solve_assignment")

`solve_assignment(cost) -> UnivariateIntArray | None` — чистая функция без сведений о таблице:

1. `NaN` или $-\infty$ в `cost` — `ValueError`: ошибка в коде.
2. Передаёт `cost` в `linear_sum_assignment` как есть: $+\infty$ scipy понимает как запрет.
3. `ValueError` от scipy — раздачи без запретов нет, возвращает `None`; иначе перестановку.

Тестируется юнитами на литералах и свойством против полного перебора; `HungarianMatcher` — на поддельной таблице и интеграционно. Исключение бросает не она, а сопоставитель: причины знает только таблица.

(init-impossible-pairs)=
**Невозможные пары** — пары с $\ell_{jc} = -\infty$ в двух {ref}`состояниях <init-pair-states>`: «не покрывает кластер» (`Exponential(0.5)` по `{−1, 5}`) и «не оценена» (`Exponential` на кластере с отрицательным средним даёт `lambda_ < 0`). `HungarianMatcher` запрещает обе. `IdentityMatcher` на $\ell_{jc}$ не смотрит: «не покрывает» он пропускает, и годность смеси решает проверка результата — точку может покрыть соседняя компонента.

**Запрет — $+\infty$, а не конечный штраф.** scipy не выбирает такие пары и бросает `ValueError` «cost matrix is infeasible», только если раздачи без них нет. На `NaN` он бросает тот же тип, и различить можно только по тексту, поэтому `solve_assignment` отвергает `NaN` и $-\infty$ заранее; после этого `ValueError` от scipy значит только «нет раздачи»: других причин у него нет, матрицу строит сопоставитель, она квадратная и числовая. Конечный штраф хуже: при стоимостях порядка $3 \cdot 10^{16}$ он неотличим от максимальной стоимости, и раздача без запретов теряется.

**Почему не жадный алгоритм:** ранний выбор может отнять у семейства единственный подходящий кластер. В гетерогенных смесях это типично: `Normal` подходит почти к любому кластеру, `Exponential` — только к «своему». Скорости жадный не даёт: время уходит на заполнение таблицы, а венгерский алгоритм на $10 \times 10$ работает микросекунды.

```{admonition} Пример: жадный выбор
:class: tip

| $\ell_{jc}$ | A | B |
| --- | --- | --- |
| `Normal` | −100 | −110 |
| `Exponential` | −105 | −1000 |

Жадный выберет `Normal` ← A и в сумме получит −1100; оптимум — `Normal` ← B, `Exponential` ← A, −215.
```

## Критерий по смеси: `ExhaustiveMatcher`

Позже, см. {ref}`«Первая версия» <init-first-version>`.

Раздачу можно оценивать правдоподобием всей смеси из оценённых компонент:

$$
\log L(\sigma) = \sum_{i=1}^{n} \log \sum_{j=1}^{k} \pi_{\sigma(j)} f_j\bigl(x_i \mid \hat\theta_{j\sigma(j)}\bigr).
$$

Критерий учитывает перекрытие компонент, но неаддитивен (логарифм снаружи суммы), поэтому венгерский алгоритм здесь не точен и раздачи перебираются. Перебираются только различимые — для группы одинаковых семейств важно лишь множество её кластеров, — поэтому вариантов

$$
\frac{k!}{m_1!\, m_2! \cdots m_d!},
$$

где $m_g$ — кратность семейства $g$: 5 `Normal` и 5 `Exponential` дают 252 варианта, а не $10!$.

- **Стоимость:** таблица общая, вариант стоит одно $\log L$, $O(nk)$, через метод таблицы `mixture_loglikelihood(assignment)`, который добавится в протокол.
- **Невозможные пары:** раздачи с ними пропускаются; если не осталось ни одной — `InitializationError` с причинами, как у `HungarianMatcher`.
- **Предел перебора:** больше `max_candidates` вариантов — `ValueError`, а не долгий перебор: число вариантов зависит только от `families`, другое разбиение не поможет.

**AIC и BIC здесь не нужны:** число параметров одинаково для всех раздач, поэтому AIC и BIC смеси выбирают ту же раздачу, что `ExhaustiveMatcher`, а сумма покомпонентных AIC сводится к критерию `HungarianMatcher` и как критерий качества некорректна (разбиение тоже подобрано по данным). Информационные критерии нужны при сравнении структур — это `structure_selection`.

## `IdentityMatcher`

`_match` возвращает `[0, 1, …, k-1]` без обращения к таблице; `_order` переопределён и ничего не меняет — порядок одинаковых семейств задаёт способ разбиения.

- **Нужен** со способом разбиения, который кладёт кластер для `families[j]` в столбец `j` (пока только пользовательским, см. {ref}`«Отложено» <init-deferred>`). Такой способ может осознанно разложить и одинаковые семейства: у `[normal, normal]` широкий фон (среднее 5.1) в столбце 0 и узкий пик (5.0) в столбце 1 — `_order` по умолчанию поменял бы их местами, и настройки `ECM` для фона молча ушли бы к пику.
- Со способами, не знающими семейств, раздача случайна: номера кластеров `KMeansPartitioner` от запуска к запуску разные.
- Пару «не оценена» не обходит: её `ComponentEstimationError` прервёт сборку смеси, мультистарт пропустит запуск. «Не покрывает кластер» пропускает.

(init-speedup)=
**Ускорение.** Пока не делается. Если узким местом станет заполнение таблицы, считать $\ell_{jc}$ по подвыборке кластера — необязательным параметром сопоставителей или отдельной реализацией.
